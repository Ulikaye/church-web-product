# General Church Website Product — Plan & Documentation

## Goal
Build one reusable church website product that can be customized and sold to individual churches, starting with a low-cost static deployment and earning additional income from maintenance and advanced features.

## Three current showcase variants
1. `church_showcase_generic_english.html` — generic English showcase.
2. `church_showcase_generic_swahili.html` — generic Swahili showcase.
3. `northlight-homepage_tanzania_africa.html` — alternative premium/editorial design.

Treat the first two as language variants of the same product; treat Northlight as an alternative visual style.

## Version 1: include
- Responsive home page
- Church name/logo/colors
- About / vision / mission
- Service times
- Location + Maps
- Contact + WhatsApp
- Social links
- Events
- Ministries
- Sermons/media links
- Articles/news
- Gallery
- Basic SEO
- Mobile navigation
- Church-owned photographs for final client deployments

## Keep out of the cheap package
- Admin dashboard/CMS
- Database/member accounts
- Online payment integration
- Stored contact/prayer/registration forms
- Automated sermon/event management
- SMS/WhatsApp automation
- Complex search
- Mobile app
- Major bespoke animations/redesigns

These should be quoted separately.

## Image standard
| Slot | Ratio | Suggested size |
|---|---:|---:|
| Hero | 16:9 | 2400×1350 |
| Feature portrait | 4:5 | 1200×1500 |
| Gallery | 3:4 | 1200×1600 |
| Logo | 1:1 | 512×512+ |
| Card | 4:3 / 16:10 | ~1200px wide |

Prefer Tanzanian/African imagery for the showcase. For a client, replace demo photos with the church's own images.

## Client workflow
1. Demonstrate designs.
2. Choose design/language.
3. Collect church materials.
4. Agree on scope and price.
5. Customize.
6. Test desktop/mobile.
7. Client approval.
8. Connect domain/hosting.
9. Launch.
10. Maintenance.

## Business rule
A launch warranty can cover defects in your implementation. New requirements, new pages, new integrations, and ongoing content changes should be treated as maintenance or additional development.

## Technical direction
Start static. GitHub Pages is appropriate for the showcase and static sites. A backend is introduced only when persistent data, authentication, payments, CMS functionality, or automation is actually required.

## Roadmap
- Phase 1: showcase
- Phase 2: cheap client V1
- Phase 3: recurring maintenance
- Phase 4: CMS/backend
- Phase 5: integrations and automation
